---
description: Revise a foundation phase (Vision / Architecture / Backlog) when Retrospective surfaced a change that requires it. Optional — only run when retro flagged it.
---

You are the foundation revise runner. Use this command when Retrospective produced an action item that requires changing a Foundation phase output (`f1-vision.md`, `f2-architecture.md`, or `f3-backlog.md`) before the next iteration begins.

This is **optional**. Most iterations should not need it. Run it only when the retro explicitly says "Revisit X" or the user has decided a foundation change is needed.

**Communication style.** Enumerate, don't narrate — bullets and short declarative lines over flowing prose. Lead with the decision or the fact, not a preamble.

**Checkpoint approval mechanism.** The ⛳ CHECKPOINT below means: use the `AskUserQuestion` tool (per `start.md`'s Checkpoint protocol) instead of a typed reply — options `Approve` and `Request changes`, with the built-in `Other` option covering "request changes, and type what" directly. Fall back to the plain-text prompt only if `AskUserQuestion` isn't available in this session.

---

## Step 1 — Validate state

Read `.project-artifacts/state.md`.

- If it does not exist: stop and say "No pipeline found. Run `/agile-dev:start` or `/agile-dev:improve` first."
- The revise is allowed only at `current_phase: Idle` — i.e. between iterations, with no iteration in flight. If `current_phase` is anything else, refuse: "Cannot revise a foundation phase mid-iteration. Finish or recover the current iteration first."

---

## Step 2 — Pick the phase to revise

`$ARGUMENTS` may carry a `--from <path>` suffix naming a delta-source file (e.g. a SPIKE epic's findings document — see Step 3). Strip it before reading the phase name.

If what remains **matches one of the three phase names** (`vision`, `architecture`, or `backlog`, case-insensitive), use it. Otherwise — empty, whitespace-only, a stray keystroke, or text that doesn't match any of the three — **stop and ask**, do not guess which phase was meant:

> "Which foundation phase needs revision?
> 1. Vision — `f1-vision.md`
> 2. Architecture — `f2-architecture.md`
> 3. Backlog — `f3-backlog.md`"

Refuse anything outside this list. Foundation Environment is regenerated by re-running its phase rather than revised in place — point the user at `/agile-dev:start` or manual `.devcontainer/` edits if needed.

---

## Step 3 — Re-run the phase from the existing artifact

Load the relevant phase file and the existing artifact:

| Phase | Phase file | Artifact |
|---|---|---|
| Vision | `${CLAUDE_PLUGIN_ROOT}/pipeline/vision.md` | `.project-artifacts/f1-vision.md` |
| Architecture | `${CLAUDE_PLUGIN_ROOT}/pipeline/architecture.md` | `.project-artifacts/f2-architecture.md` |
| Backlog | `${CLAUDE_PLUGIN_ROOT}/pipeline/backlog.md` | `.project-artifacts/f3-backlog.md` |

**If `--from <path>` was given:** read that file (e.g. a SPIKE epic's findings document and its foundation-impact section) and use its content as the delta directly — present a one-line summary of what you read and ask the user to confirm it's the right delta, rather than asking them to re-describe a change that's already written down:

> "Using the foundation-impact section from `<path>` as the delta for <phase>: `<one-line summary>`. Confirm, or describe what's different? (confirm / describe differently)"

**Otherwise, ask the user directly:**

> "What needs to change in <phase>? Summarise the delta — I'll start from the current artifact, not from scratch."

Wait for the answer.

Re-run the phase **starting from the existing artifact** — not from a blank slate. Apply the user's delta, ask clarifying questions only where the change creates ambiguity, and produce an updated artifact.

For complex revisions (large architecture rework, big backlog re-prioritisation), delegate the rewrite to a subagent and review the result yourself before the checkpoint.

⛳ CHECKPOINT: present the updated artifact and wait for APPROVE.

---

## Step 4 — Cascade downstream

Foundation phases depend on each other. After approving the revision, walk forward and ask whether downstream phases need a follow-up revision:

| Revised | Downstream to check |
|---|---|
| Vision | Architecture, Backlog |
| Architecture | Backlog (epics tied to old stack/components), Environment (devcontainer/dependencies) |
| Backlog | (none — but flag any in-progress iteration's epic that was changed) |

For each downstream phase, ask:

> "Does **<downstream phase>** also need revision based on this change? (yes / no / open it for review)"

- **yes:** loop back to Step 2 with that phase as the next target.
- **no:** skip.
- **open it for review:** run the phase definition's review questions only — surface anything affected; if the user spots a gap, treat as yes.

Environment changes (e.g. new runtime dependency, changed stack) should be flagged: the user must regenerate `.devcontainer/` and reopen the project. Do not regenerate it inside this command.

---

## Step 5 — Update state.md

For each revised artifact:

1. Update the corresponding row in `Completed foundation phases` with a revision marker, e.g. `Architecture ✓ (revised <YYYY-MM-DD>) → .project-artifacts/f2-architecture.md`.
2. If Backlog was revised, sync the `Backlog` table in `state.md` with the updated `f3-backlog.md`.
3. Append a one-line note to a `Foundation revisions` section in `state.md` (create on first revision):

```markdown
## Foundation revisions
| Date | Phase | Reason | Triggered by |
|---|---|---|---|
| 2026-04-29 | Architecture | Switched DB from SQLite to Postgres for concurrency | Retro of iteration 003 |
```

---

## Step 6 — Report

Tell the user:
- Phases revised (and downstream phases checked)
- Whether Environment needs regeneration (and how)
- Next step: "Run `/agile-dev:iterate` to start the next iteration with the revised foundation."
